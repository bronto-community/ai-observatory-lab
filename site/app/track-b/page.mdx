# AI for Observability: build your own AI SRE

Build an investigating agent in seven steps: a loop, an identity, eyes (Bronto MCP), a mouth (a GitHub issue),
better instructions, a better model, and the code. It works a real incident on **Storefront**, a small online shop
whose telemetry runs continuously in a shared Bronto demo org.

<Deck src="https://aisre-lab.vercel.app" title="Track B slides" />

<Callout tone="note" title="The demo incident runs on a schedule">
Every hour, Storefront runs normally until **:15**, then a new release of `checkout-api` ships and checkouts get
slow until the top of the hour. For the best investigation, ask between **:20 and :59**. Then there's a quiet
baseline to compare against and a live incident.
</Callout>

## Before you start

You need the `ai-observatory` folder and `.env` from [Start here](/start), and your AWS credentials in the
terminal (setup step 11). Two extra accounts:

- **GitHub**: an account, and a new empty **public** repository for the agent's reports, for example
  `ai-sre-issues`.
- **A GitHub token**: [create a fine-grained token](https://github.com/settings/personal-access-tokens/new),
  **Only select repositories →** your `ai-sre-issues`, permission **Issues: Read and write**. Public repositories,
  like Storefront's code, can always be read.

## Step 5: better instructions

<Steps>
<Step n={11} title="Teach it how you investigate" then="my.md has three more rules.">

Add these to the end of `my.md`:

```md
- Slow is broken too: compare latency (p50, p95) before and after, not only errors.
- Compare against a quiet window earlier the same day.
- Look for `deploy` spans near the onset: they name the commit that went live.
```

</Step>
<Step n={12} title="Restart step 4 and ask again" then="a second issue: better, worse, or out of context?">

**Ctrl-C** and run step 4 again (the prompt files are read at start-up). Ask: **"Customers say checkout got slow in
the last 30 minutes. What is going on?"**

</Step>
</Steps>

## Step 7: the code

<Steps>
<Step n={14} title="Start step 7 (terminal 1)" then="it's running. Leave it.">

**Ctrl-C**, then the step 5 command with `step-7`. The agent can now read Storefront's source on GitHub, and every
service reports the commit it runs.

</Step>
<Step n={15} title="Ask again (terminal 2)" then="does it find the deploy, open the release, and pick the right commit?">

Ask: **"Customers say checkout got slow in the last 30 minutes. What is going on?"** The release has three commits,
and two of them are decoys. If it stops at the deploy, ask the follow-up: **"Which change in that release caused it?
Read the code."**

</Step>
</Steps>

## What you built, and what's next

A trigger (your curl), a loop (Strands on Bedrock), context (the prompt files), tools (Bronto and GitHub MCP), and an
output (a GitHub issue). The managed version of all of this is
[AWS DevOps Agent](https://docs.aws.amazon.com/devopsagent/). Having built one, you know what's inside, and what it
can't see.
